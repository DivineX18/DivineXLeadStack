# V1 known limitations

Recorded at the pre-beta certification pass (2026-09-11). Everything here is
**known, deliberate, and not a blocker** — each entry is something a customer
could hit, written down so nobody rediscovers it as a surprise and so the public
promise stays inside what the product does.

Fixing any of these is V1.1 work. None may be closed by changing customer state
without an explicit migration policy.

---

## P2 — Rebuilding a funnel leaves the previous follow-up active

**What happens.** `create_funnel` always calls `createWorkflowServerSide` and
compiles a fresh follow-up workflow. It does not look for a follow-up workflow
already attached to an earlier build of the same campaign, and it does not
retire one. Rebuild a funnel three times and the workspace holds three active
follow-up workflows.

**Why it usually stays invisible.** Each workflow triggers on
`form.submitted` scoped to the form id created alongside *its own* funnel, so a
lead who opts in once enters exactly one sequence. The duplicates only surface
when the same person submits more than one of the funnels — or when the operator
leaves several builds published and traffic splits across them.

**How it surfaced.** Observed in the QA workspace on 2026-09-11: three nurture
emails arrived 5 and 35 minutes apart. The cadence was never wrong. Each
workflow fired its own day-1 email exactly 86400s after its own enrolment
(`w1 wait:86400s` → next history entry at +86401s); the enrolments were minutes
apart because the funnel had been rebuilt during testing and one test address
went through all three forms.

**What it is NOT.** Not a wait bug, not a delay-unit bug, and not a reason to
change the compiler's cadence. Authored cadence is instant transactional
delivery, then 24h, then 48-96h, and it executes exactly as authored.

**Why it was not fixed in this pass.** Retiring a workflow is a write to live
customer automation state. Auto-archiving on rebuild would silently stop
sequences that real leads are mid-way through. That needs a stated migration
policy and an operator-visible decision, not an inferred one.

**Shape of the V1.1 fix.** Most likely: carry the campaign identity across
rebuilds and, on rebuild, offer the operator a choice — supersede the previous
follow-up (archive it) or keep both — defaulting to supersede but never acting
silently. `applyWorkflowPlan` already accepts a `workflowId` and overwrites in
place, so the mechanism exists; what is missing is the link from a new funnel
build back to the previous build's workflow.

## P2 — A form is live the moment it is created

`createFormServerSide` writes `enabled: true` (`src/lib/server/forms-service.ts`),
so a form created by `create_form` is reachable at `/f/[id]` immediately. Every
other generated object in the create path is a draft: funnels are `status:
"draft"`, workflows are `status: "draft"`, booking pages are `status: "draft"`.

This is safe — a form only collects, it never sends, charges, or publishes a
claim — but it is an inconsistency in the review boundary, and the certification
records it rather than describing all create paths as draft-first.

## V1.1 — Growth Scan history is fetched and then dropped in 2 of 3 prompt paths

`buildIntelligenceContext(..., { includeScanHistory: true })` retrieves the last
scans and formats them (`intelligenceOrchestrator.ts`, the
`=== GROWTH SCAN HISTORY ===` block). The CRO-audit path consumes it. Two paths
fetch it and then omit it from the concatenated system prompt:

- `artifacts/api-server/src/routes/zeno.ts` — Zeno chat assembles the system
  prompt from several parts; `scanHistory` is not one of them.
- `artifacts/api-server/src/routes/zeno.ts` — blueprint generation fetches with
  `includeScanHistory: true` and then uses only `knowledgeContext` +
  `calibrationNotes`.

Consequence: Zeno chat and blueprint generation cannot see that the same finding
was already given to this business last month.

**Deliberately deferred.** The edit is small — one string added to a
concatenation in each place — but it changes what the model is reasoning over on
the two highest-traffic prompt paths, and prescription integrity is exactly the
property that must not regress. Shipping it needs a real-model run of the
integrity battery, not a source assertion, so it is V1.1 rather than a drive-by.

## V1.1 — Asset Studio output is prose, so it has no structured execution path

Assets generated by Ascend's Asset Studio (`generated_assets.content`) are a
single markdown blob. There is no structured variant, and the one markdown
parser in that repo (`EmailSequenceView.tsx`'s `parseEmailSequence`) does not
match the format the generator actually emits.

This is why written assets are **export-only** and are labelled as such in the
product: the asset viewer and `create_asset`'s reply both say the asset is copy
to use elsewhere, and point at Zeno for anything that should become a real draft.

**This is not the Create → Execute path.** A customer acting on a diagnosis goes
recommendation → `FixWithZenoButton` → Zeno → `create_funnel` /
`create_form` / `create_booking_page` / `apply_workflow_plan`, which write real
Flow drafts. That path is verified by
`scripts/verify-ascend-execute-bridge.mts`. Asset Studio is a second, parallel
writer whose output was never wired to execution.

**Shape of the V1.1 fix.** Add a `jsonMode: true` structured variant to asset
generation and store the JSON alongside `content` — the machinery already exists
and is proven for `zeno_blueprints`. Regexing prose is the alternative and is
the worse one.

## V1 measurement boundary (public-claim constraint)

Ascend surfaces the Growth Score, the primary constraint, category scores,
action-item status, and a per-business growth timeline. Flow surfaces revenue,
pipeline, win rate, new leads, per-page visitors/sign-ups/conversion rate, and
source/campaign attribution for leads.

**There is no attribution from an executed recommendation to an outcome.** No
identifier links a generated draft to the finding it was meant to fix, and the
Intelligence Bridge is one-directional, so Flow's performance data has no route
back to Ascend.

Public messaging may claim measurement only for the metrics above. It may not
claim closed-loop learning or autonomous optimisation.
